# Embedded knowledge notes — session 2

## 1. Finding the port, the offset, and what value to write

Recipe, in order, whenever you need a peripheral to do something:

1. **State the need in plain words.** e.g. "this pin as digital output,
   push-pull, no need for speed" or "that pin as input with pull-up". Any
   port (A-G), any pin (0-15) — the recipe below doesn't change.
2. **Find the peripheral base address.** RM0008 Table 3 ("Memory map") —
   e.g. GPIOC base = `0x40011000`.
3. **Find the register that controls that behavior**, and its offset, from
   that peripheral's register-map table (e.g. Table 59 for GPIO):
   - `CRL`/`CRH` (offset `0x00`/`0x04`) — pin mode/config (input, output,
     speed, pull-up/down, analog...)
   - `ODR` (offset `0x0C`) — direct output level, all 16 pins
   - `BSRR` (offset `0x10`) — atomic set/reset, one pin at a time
   - `IDR` (offset `0x08`) — read input level
4. **Find which bits are "yours"** inside that register. CRL/CRH give each
   pin a 4-bit slot: `CNF[1:0]` + `MODE[1:0]`, at bit offset `(pin % 8) * 4`
   (CRL for pins 0-7, CRH for pins 8-15).
5. **Look up what value encodes your need**, from the bit-field
   description right below the register (RM0008 9.2.1/9.2.2, "Port bit
   configuration table"):

   | Need | MODE[1:0] | CNF[1:0] |
   |---|---|---|
   | Output, push-pull, 10MHz | `01` | `00` |
   | Input, floating (reset state) | `00` | `01` |
   | Input, pull-up or pull-down | `00` | `10` |

6. **Write it with a mask**: clear the old 4 bits, OR in the new value —
   never write the whole register (you'd clobber every other pin's config):
   ```c
   GPIO_CRL &= ~(0xF << (pin * 4));   // clear this pin's nibble
   GPIO_CRL |=  (val << (pin * 4));   // set new mode/cnf
   ```

**Gotcha worth knowing**: pull-up vs pull-down is *not* a separate bit in
CRL/CRH. `CNF=10` just means "input with pull resistor" — which direction
(up or down) is chosen by the corresponding bit in **ODR**: `1`=pull-up,
`0`=pull-down. Same register we already use for output, doing a second job
depending on the pin's mode.

## 2. How the embedded project boots and runs

### The vector table

Cortex-M chips don't run a bootloader-style "jump to main" — on reset, the
CPU hardware reads two 32-bit words straight from address `0x00000000`
(mapped to flash start, `0x08000000`, by the BOOT pins):

- word 0: initial stack pointer value
- word 1: address to start executing (the reset handler)

That's it, no code runs before this — the *data* at those two addresses
sets up the CPU directly. In `main.c` that's the `vector_table[]` array,
placed first via `__attribute__((section(".isr_vector")))`. Most bare-metal
projects write this table in a separate `startup.s` assembly file; we skip
the `.s` file entirely by declaring it as a C array of function pointers —
same result, GCC-specific shortcut, works because Cortex-M's reset doesn't
actually require hand-written assembly (unlike e.g. x86).

A real project's vector table has entry 0 (initial SP) followed by 15
Cortex-M system exceptions (NMI, HardFault, SysTick...), then
per-peripheral IRQs after that — ours only has 2 entries (SP + reset
handler). Fine while nothing triggers an exception; if one ever does (bad
memory access, div-by-zero on some cores, unmasked interrupt), the CPU
reads garbage as an address and jumps into nowhere — silent hang, no
message. Add the full table before enabling any interrupt.

### The linker script (`link.ld`)

Two jobs:

1. **`MEMORY` block** — declares the physical address ranges that
   actually exist on this chip (from the datasheet): `FLASH` at
   `0x08000000` (64K), `RAM` at `0x20000000` (20K). The linker refuses to
   place anything outside these.
2. **`SECTIONS` block** — decides where each chunk of the compiled program
   lands:
   - `.isr_vector` → start of FLASH (must be first — that's what the CPU
     reads on reset)
   - `.text`/`.rodata` (code, string/const literals) → FLASH
   - `.data` (globals with a non-zero initial value) → lives physically in
     FLASH (`AT> FLASH`, so the initial values survive power-off) but is
     *linked* to run from RAM (`> RAM`) — needs copying at startup
   - `.bss` (uninitialized/zero-initialized globals) → RAM only, takes no
     space in the flash image at all

The `_sidata`/`_sdata`/`_edata`/`_sbss`/`_ebss` symbols in the script are
just markers (addresses) the C code reads to know where each region starts
and ends — the linker doesn't run this copy, it only sets up the addresses.

### The reset handler and main loop

`reset_handler()` does the copy the linker script set up for, then calls
`main()`:
```c
// .data: flash -> RAM (restore initial values of globals)
while (dst < &_edata) *dst++ = *src++;
// .bss: zero it (C guarantees globals start at 0)
while (dst < &_ebss) *dst++ = 0;
main();
```
This is normally done for you by the C runtime startup (`crt0`) before
`main()` — but that comes from libc, and we build with `-nostdlib`
(no libc at all, smallest possible image), so we hand-roll the two loops
libc would've run.

`main()` itself never returns — no OS to return *to*. It ends in
`for (;;) { ... }`, the whole program. `reset_handler`'s trailing
`while (1);` is just a safety net in case `main` ever somehow falls
through — traps the CPU instead of executing whatever garbage comes next
in flash.

### Compiler vs linker, at a glance

`arm-none-eabi-gcc` invoked with `-T link.ld` does both steps in one
command: compiles `main.c` to an object file (machine code + a list of
unresolved symbols/sections), then hands off to the linker, which places
every section per the script and bakes real addresses into the final
`.elf`. `openocd`'s `program` command reads that `.elf` directly and
flashes only its loadable sections — no separate `objcopy` step needed
unless a flashing tool specifically wants a raw `.bin`.
